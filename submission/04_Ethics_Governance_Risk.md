# RevenuePulse AI - Ethics, Governance and Risk Note

**Scope:** a decision-support prototype for B2B account-risk prioritisation. All
current data is synthetic. No customer contact, pricing, offer or CRM action is
performed by the system.

## 1. Synthetic vs real-data boundary

- Every account history, revenue value, engagement score and label in this
  repository is generated by `src/data/generate_synthetic.py`.
- Model metrics (Precision@50 0.540, PR-AUC 0.382, Brier 0.094) are properties of
  that generator and must not be presented as real-world performance.
- The generator produces a counter-intuitive relationship: positive six-month revenue
  growth precedes a later 20% give-back. The fitted models learn this direction. It
  may not exist in real accounts, and that is a primary reason the recommendation is a
  controlled pilot rather than scaling.
- Real-data use requires a new data-protection review, a new evaluation, and a new
  model card. Nothing in this repository transfers automatically.

## 2. Privacy and data minimisation

| Control | MVP state | Pilot requirement |
|---|---|---|
| Personal identifiers (names, emails, phones) | Absent from schema; validator rejects such columns | Confirm in the client extract |
| Account identifiers | Synthetic `account_id` only | Pseudonymised client IDs |
| Data granularity | Monthly aggregates | Keep monthly aggregates; no contact-level data |
| Transfer | Local files only | Encrypted transfer channel |
| Retention | Local git-ignored files | Delete raw client data 30 days after readout |
| Access | Local machine, no auth | Role-based access, least privilege |
| Logs | Local SQLite review log | Audit log with access controls, no customer content |
| LLM/data egress | No LLM, no network calls at runtime | Keep LLM disabled by default; any egress requires approval |

## 3. Prediction errors

- **False positives:** the queue spends review time on accounts that do not decline
  materially. On synthetic test data, 23 of 50 reviewed accounts did not cross the
  label threshold; 8 of those 23 had declined by less than 20%.
- **False negatives:** declines outside the queue are missed. Recall@50 is 0.287, so
  most decliners are outside a 50-account queue by design.
- **Label error:** the target is a 20% three-month revenue move, not churn. A
  seasonality or billing-timing drop counts the same as a retention failure.
- **Presentation:** medium risk is shown as "Review recommended", not as a
  probability of loss; every page states the score is a prioritisation signal.

## 4. Biased prioritisation and fairness

- Segment results are reported (Enterprise / Mid-Market / SMB) but segment labels are
  synthetic and sample sizes are small; this cannot establish fairness.
- Real protected attributes (industry, region, firm size, tenure) are not in the data.
  A real pilot must test whether prioritisation systematically deprioritises a
  customer group and must define an escalation path if it does.
- The model ranks accounts, not people. No individual is scored.
- Thresholds are configurable so a client can trade recall against review capacity
  without retraining.

## 5. Automation bias and human override

- The AI output is a suggestion with evidence; accepting, editing or dismissing is
  mandatory for a recorded decision.
- The queue shows review status so unreviewed high-risk accounts are visible.
- Editing is first-class and both the AI suggestion and the human amendment are
  stored.
- Known risk: a confident score suppresses independent judgement. Mitigations for a
  pilot: require a note on high-risk dismissals, sample-audit accepted suggestions,
  and review override rates as a trust metric.
- The MVP does not measure override rates; that is a pilot metric.

## 6. Explainability

- Reason codes are deterministic rules over the account's own features; a reviewer can
  verify each claim against the row.
- Wording is association-only: "factors associated with the risk score include ...".
  No causal claim is made and no intervention effect is implied.
- No LLM generates explanations, so no fabricated rationale can appear.
- The counter-intuitive dominant driver (six-month revenue growth) is disclosed in the
  model card and the review queue's context, not hidden.

## 7. Auditability

- Every accept / edit / dismiss writes timestamp, account, snapshot date, risk score,
  risk band, model name, AI recommendation, decision, edited recommendation and
  reviewer note to `runtime/review_feedback.db`.
- The queue and log export to CSV for meeting records.
- Limitations: no authentication, no user identity beyond a placeholder, no
  tamper-evidence, no retention policy enforcement. Production requires all four.

## 8. Model drift and monitoring

Required before any real pilot:

- input drift on the top drivers (six-month revenue trend, engagement level, activity
  recency) and missing-rate of engagement;
- calibration drift (Brier score, bin gaps) per review window;
- Precision@K, lift and false-alarm rate per window against a frozen baseline;
- label prevalence monitoring and a periodic review of the materiality definition;
- a documented retraining cadence and a rollback path.

None of this is implemented in the prototype. It is a stated gap, not an assumption.

## 9. Misuse and prohibited uses

Prohibited:

- automated customer contact, offers, discounts or pricing changes;
- automated account termination, downgrade, collections or credit decisions;
- employment, individual-customer or personal-data decisions;
- presenting scores as churn facts or as real-world validated performance;
- training on real customer data without privacy and governance approval;
- use as the sole basis for a commercial decision without human review.

Technical guardrails in the MVP: no outbound integration exists; no LLM is enabled;
config validation refuses to enable LLM or opportunity-scoring flags; a test scans the
product layer for outbound tokens (SMTP, webhooks, CRM SDKs). These are deterrents,
not a security boundary - a determined operator with code access could add an
integration, which is why governance controls are required alongside code.

## 10. Controls summary

| Control | Status |
|---|---|
| Minimum necessary data | Design principle; synthetic schema has no personal data |
| No personal contacts | Enforced by schema validation |
| Encryption | Required for pilot; not applicable to synthetic demo |
| Deletion policy | Stated for pilot (30 days); not automated |
| Role-based access | Not implemented; pilot blocker |
| Audit logs | Implemented locally (SQLite) |
| Human approval | Implemented (accept / edit / dismiss required) |
| Configurable thresholds | Implemented in `config.yaml` |
| Model monitoring | Not implemented; pilot blocker |
| Periodic validation | Design described; not scheduled |
| Rollback / disable | Stop using the queue; no source-system writes exist |

## 11. Launch blockers (STOP conditions)

Do not proceed past a pilot if any of the following holds:

- no meaningful lift over a transparent scorecard or the client's existing rule;
- false-alarm rate unacceptable to the reviewers who must use the queue;
- poor reviewer acceptance or the queue is ignored in practice;
- data access or onboarding makes the economics uneconomic;
- privacy or governance cannot be controlled to the client's standard;
- no measurable workflow benefit (triage time or decision quality);
- real-data model performance materially fails, including if the synthetic
  growth-to-give-back pattern does not reproduce.

Each blocker is a stop, not a reason to retune on the evaluation window.
